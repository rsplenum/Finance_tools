FinSight · Architecture decision record + implementation specification

One project model. Two report depths. A deterministic report factory.

Detailed technical architecture and phased implementation specification based on the selected product direction: both standard bankable project reports and detailed DPRs, with selective runtime AI and AI-intensive engineering-time development.

Decision baseline: 15 November 2026Existing stack: Astro 7 · Preact · TypeScript · Tailwind 4Cloudflare: Workers · D1 · KVTesting: Vitest · PlaywrightDevelopment: Claude Code + agents
Architecture decision

Build a deterministic core with optional AI services around it.

Standard report generation must work with zero LLM inference. Detailed DPR generation uses the same canonical project model and core calculations, with deeper technical modules, evidence requirements and annexes. AI is an optional assistant for extraction, research and difficult narrative—not the authority for calculations, facts or report structure.

02 · Architecture principles

Non-negotiable engineering rules.

P01

One canonical project model

All inputs, evidence, assumptions, calculations, narrative references and document outputs must resolve to a versioned project model. No report section should maintain its own conflicting copy of a financial value.

P02

Pure calculation functions

Core financial and technical calculations should be deterministic functions with explicit inputs and outputs. No network, UI, database or LLM dependency inside the calculation domain.

P03

Evidence-aware claims

Every material claim is linked to a source, user assertion, quotation, calculation or explicit assumption. The system must not convert unverified input into verified fact through polished prose.

P04

Rules before generative choice

Report inclusion, exclusions, required fields and standard interpretations are controlled by versioned rules. AI may suggest but cannot silently override them.

P05

One semantic document tree

HTML preview and PDF export must be generated from the same report representation and metric bindings. Avoid separate HTML and PDF logic that drifts.

P06

Reproducible releases

Every generated report records schema, engine, rules, content library and renderer versions, plus the immutable input snapshot used to generate it.

P07

AI is an adapter, not a dependency

Core product functionality must continue if an AI provider is unavailable, expensive, rate-limited or disabled. AI-assisted tasks degrade gracefully to manual structured entry.

P08

Progressive depth

Standard reports collect the minimum evidence required for a credible bankable proposal. DPR mode activates deeper technical, environmental, implementation and annex requirements where applicable.

Presentation layer

  • Astro pages for routing, static content and server-rendered shells.
  • Preact islands for project wizard, calculators, evidence review and report preview.
  • Tailwind CSS 4 plus FinSight design tokens and semantic component library.
  • UI state is not the authoritative storage for calculations or payment entitlements.

Application/API layer

  • Cloudflare Workers expose authenticated, versioned API routes.
  • Validate request schemas at the boundary.
  • Enforce user, organisation, project and document permissions.
  • Orchestrate calculation, report build, export, AI tasks and payment status.

Domain layer

  • Pure TypeScript packages: project model, finance, technical modules, rules, evidence and report composition.
  • No UI imports and no direct Cloudflare bindings in domain packages.
  • Decimal-safe monetary arithmetic, explicit units and periods.
  • Deterministic versioned outputs.

Persistence and artefacts

  • D1 for relational metadata, project records, report manifests, evidence metadata and job state.
  • KV for cache/configuration only—not the source of truth or financial ledger.
  • Object storage (Cloudflare R2, subject to current account and deployment verification) for uploaded source documents and generated artefacts.
  • Queues for long-running extraction/rendering jobs if volume justifies asynchronous processing.

04 · Canonical project data model

Model facts, assumptions, evidence and calculations separately.

This separation is the most important data-design decision. A project fact is not the same thing as a model assumption; a source document is not the same thing as a verified claim; a calculated metric is not a manually typed number.

Required data semantics

  • Represent money with explicit currency and scale; use decimal-safe arithmetic and controlled rounding.
  • Represent quantities with units; never infer whether 10 means kg, tonnes, units or lakh rupees.
  • Represent financial periods explicitly: Indian financial year, month, quarter, date and forecast year.
  • Distinguish unknown, not_provided, not_applicable and numeric zero.
  • Each assumption must record whether it is user-entered, extracted, externally sourced or defaulted from a reference library.
  • Every external reference datum must have source, observation date, geography, applicability and expiry/review policy.
  • Never overwrite an issued report's input snapshot. Changes create a new project revision and report build.

05 · Calculation and domain engines

Build a shared financial core, then industry-specific technical modules.

Financial core: shared across report depths and product modules

SubsystemResponsibilitiesOutputs / invariants
Project costLand, building, plant, installation, preliminary expenses, contingency, margin for working capital.Cost head totals; source and timing; total project cost reconciliation.
Means of financePromoter contribution, term loan, subsidy/grant if eligible, unsecured loans and other funding.Sources equal uses; eligibility and timing conditions explicit.
Operating modelVolume, price, capacity ramp, product mix, variable/fixed costs.Revenue and cost drivers by period and product.
Working capitalInventory, receivables, payables, operating cycle, margin and bank finance assumptions.Working capital requirement and cash conversion cycle; avoid double-counting.
Depreciation and taxAsset classes, useful life/method, tax assumptions and applicable regime.Versioned schedule; tax rules require dated professional review.
Debt scheduleDrawdown, moratorium, interest, repayment frequency, fees and balance.Opening + drawdown − repayment = closing debt; interest reconciles to schedule.
StatementsProjected P&L, balance sheet and cash flow.Balance sheet balances; cash movement reconciles; retained earnings roll forward.
ViabilityDSCR, break-even, debt service, cash accrual and sensitivities.Every ratio has explicit definition and numerator/denominator lineage.
Scenario engineApply shocks to underlying drivers and recalculate dependent schedules.Whole-model recomputation, not manually adjusted chart values.

Technical engine modules

Manufacturing

Installed/practical capacity, shift and working-day calendar, process routing, cycle time, yield, rejection, material consumption, machine load, utilities, labour and bottleneck analysis.

Trading

SKU mix, purchase/sales margin, stock days, supplier/customer credit, shrinkage, inventory funding, turnover and concentration.

Services

Billable capacity, staff utilisation, service hours, rate card, client ramp, contract coverage, delivery costs and receivables.

Construction

BOQ quantities, material/labour rates, work packages, contractor costs, milestones, retention, escalation and cash-flow timing.

Food processing

Input-output ratios, batch yields, process loss, packaging, cold storage, quality controls, utilities and seasonality.

Hospitality

Room/seat capacity, occupancy, average rate, covers, seasonality, channel commission, staffing and fixed operating costs.

Do not hard-code generic “industry norms” as truth. Technical modules need explicit assumptions, source metadata, geography and effective dates. A reference range can inform a user but must not silently replace project-specific evidence or supplier specifications.

Exhibit selection rule

An exhibit is included only if it answers a decision question and adds information not already communicated more clearly by a nearby table. Each exhibit declares its source metric IDs, units, period, title, interpretation and print constraints. A chart is not selected just because a dataset exists.

07 · Selective runtime AI architecture

AI services are optional, bounded and non-authoritative.

Zero-AI default

Core report build

Project data → calculation engine → rule engine → content composition → validation → HTML/PDF. No LLM call in this path.

Optional AI adapter

Document extraction

Uploaded quotation or licence → extraction proposal → schema validation → user confirmation → canonical project model. AI output is never automatically treated as verified fact.

Optional AI adapter

Evidence-assisted narrative

Approved facts and source excerpts → constrained draft → metric-token validation → claim/source checks → user approval. The model cannot invent numbers or change calculation outputs.

Optional AI adapter

Research assistance

Explicitly requested research → retrieved dated sources → extracted claims → source register → user review. No unsourced market-size or competitor assertions.

AI task contract

type AiTaskRequest = {
  taskId: string;

  usage: { inputTokens: number; outputTokens: number };

};

Guardrails

  • Do not send full project data to an AI provider when only a single document or paragraph is needed.
  • Redact unnecessary personal, financial-account and identity data before external processing.
  • Require explicit user action for optional AI tasks and explain the purpose.
  • Use strict JSON schemas and validate outputs before they enter the project model.
  • All extracted facts remain “unconfirmed” until validated by deterministic checks or user approval.
  • Never allow AI to write directly to financial metric tables, formula registries or issued report records.
  • Store provider, model, purpose, usage, cost, consent and status for each task.
  • Provide manual entry fallback if AI is unavailable.

Persistence recommendation

  • D1: organisations, users/roles, projects, revisions, structured assumptions, evidence metadata, calculation manifests, report manifests, entitlements, AI task metadata and audit events. Design for D1 transaction and query constraints.
  • R2: source files, generated PDFs, large report artefacts and immutable export objects. Store object key, hash, size, content type and retention state in D1.
  • KV: cache static reference lookups, feature flags and non-authoritative derived cache. Never use KV as the sole store for project facts, balances or audit history.
  • Queues: optional for large PDF rendering, OCR, extraction and bulk regeneration. Jobs must be idempotent and retry-safe.
  • Secrets: provider keys and payment credentials belong in Worker secrets, never frontend bundles or repository files.
09 · Security, privacy and commercial integrity

Do not confuse hiding the PDF with protecting the data.

  • Enforce authentication, organisation/project ownership and paid entitlements at the Worker/API boundary.
  • Do not send paid report contents or full financial schedules to an unpaid browser if those are intended to be gated.
  • Use short-lived signed object URLs for exports and verify access before issuing them.
  • Separate preview data from full report data at the API contract—not merely with CSS blur or hidden UI.
  • Apply upload limits, allowed MIME types, content hashing, malware scanning and safe file handling.
  • Define retention, deletion, backup and user export policies for personal and business documents.
  • Keep audit events for project revisions, report builds, exports, payments, AI tasks and permission changes.
  • Use tenant isolation tests to ensure one organisation cannot access another organisation's projects or artefacts.
  • Document that FinSight-generated reports are promoter-prepared and do not imply independent TEV, engineering certification, audit or lender approval.
Threat-model requirement: the browser must not receive complete paid content merely because the final PDF is server-generated. If the browser can retrieve the underlying report JSON or calculation payload, the paywall is bypassable. Design preview and paid-content APIs separately.
10 · Phased implementation specification

Build in gated phases with tangible exit criteria.

0

Repository and architecture audit

Gate 0

Inspect current source of truth before designing migrations.

  • Map existing Astro/Preact/TypeScript structure, Workers routes, D1 schema, KV use and deployment bindings.
  • Inventory existing DSCR, CMA, construction estimate, project report and viability code.
  • Map formulas, duplicate logic, current tests, data contracts and report generation paths.
  • Identify current UI/API trust boundaries and any browser-exposed paid data.
  • Produce architecture map, dependency graph, risk register and reuse/deprecate decisions.

Exit: repository-backed current-state architecture document and approved target-state delta. No speculative rewrite.

1

Domain specification and canonical schema

Gate 1

Establish the common language and data contracts.

  • Define project archetypes, purposes, report depths and required fields.
  • Define units, currency scales, Indian financial-year conventions and null semantics.
  • Define project revision, evidence, assumption, calculation-run, metric and report-build schemas.
  • Define formula registry and reference-data versioning.
  • Write JSON Schema or equivalent runtime validators and migration rules.

Exit: schema reviewed with example fixtures for greenfield manufacturing, expansion, trading and services.

2

Financial core consolidation

Gate 2 · Critical

Make the shared financial engine authoritative across modules.

  • Consolidate project cost, means of finance, revenue/expense drivers, working capital, depreciation/tax assumptions, debt schedule, statements, DSCR, break-even and sensitivities.
  • Use pure functions and decimal-safe calculations.
  • Introduce stable metric IDs, formula IDs, lineage and immutable calculation manifests.
  • Remove duplicate formula implementations only after parity tests demonstrate equivalence.
  • Build independent reference cases and reconcile to manually checked examples.

Exit: golden tests, invariants, cross-module parity and no unexplained output drift.

3

Evidence and assumption system

Gate 3

Make the report honest about what is known and what is assumed.

  • Implement source registry, evidence classes, source date, issuer, scope, hash and confidence.
  • Link every material assumption and claim to evidence or a declared assumption.
  • Build missing-evidence rules and open-items register.
  • Add user confirmation and evidence status transitions.
  • Define retention, deletion and upload policy.

Exit: report can distinguish verified document, third-party source, quotation, promoter assertion, model assumption and missing evidence.

4

Manufacturing technical module

Gate 4 · First vertical

Use manufacturing to prove the full system before adding more industries.

  • Capacity, utilisation ramp, shift calendar, process routing, cycle time, yield/rejection and bottlenecks.
  • Machinery/equipment schedule and quotation basis.
  • Material consumption and supplier/lead-time records.
  • Manpower, utilities, quality and maintenance inputs.
  • Technical assumptions flow into operating costs and financial projections.

Exit: one complete manufacturing project can be modelled from project setup through technical schedules and financial projections without AI inference.

5

Rules engine and report composition

Gate 5

Generate valid report variants from reusable blocks.

  • Implement report profiles: standard and DPR.
  • Implement project-type and project-purpose rules.
  • Implement content atom contracts, conditional narrative patterns and exhibit-selection rules.
  • Build document AST and section/annex dependency graph.
  • Validate missing required blocks, incompatible modules and repeated content.

Exit: same project model generates meaningfully different standard and DPR outputs; expansion and greenfield reports differ appropriately.

6

HTML/PDF compiler and editorial QA

Gate 6

Make the output a professional document, not a decorated dashboard.

  • Shared semantic document tree for HTML preview and PDF.
  • Implement A4 typography, grid, tables, page numbers, running headers, footers and annex references.
  • Implement chart rules: every exhibit must answer a question and avoid adjacent duplication.
  • Test long tables, page splits, missing modules, images, grayscale and mobile preview.
  • Add report comparison/diff between revisions.

Exit: visual regression suite and reviewer-approved standard report and DPR specimens.

7

Optional AI adapters

Gate 7

Add runtime AI only after the deterministic workflow works.

  • Document extraction with structured proposal and user confirmation.
  • Evidence-assisted narrative for non-standard cases.
  • Optional market research with source capture and date labels.
  • AI task budgets, consent, provider/model logging, retention and fallback.
  • Prompt-injection and malicious-document handling.

Exit: AI can be disabled without breaking report generation; AI output cannot alter financial metrics or bypass evidence controls.

8

Commercial hardening and further archetypes

Gate 8

Secure, scale and expand from actual customer needs.

  • Payment entitlement and preview/full-document API separation.
  • Organisation, role and project permissions.
  • Object storage, signed URLs, asynchronous jobs and observability.
  • Add trading and services next; then construction, food processing and hospitality based on demand.
  • Measure report build time, AI cost per task, support incidents and evidence completion.

Exit: secure paid document delivery, operational metrics and repeatable module onboarding process.

12 · Operating model, observability and governance

Make the system maintainable after the first launch.

Version governance

Semantic versions for engine packages, formula registry, schemas, report rules, content library and renderer. Breaking changes require migration plans and regenerated golden outputs.

Audit trail

Record project edits, assumption approvals, evidence changes, calculation runs, report builds, exports, payments, AI tasks and permission changes.

Observability

Measure API latency, calculation duration, render duration, queue retries, report failures, validation warnings, storage use and AI spend by task.

Support diagnostics

Every report gets a non-sensitive build ID and diagnostic manifest so support can reproduce the build without exposing customer data unnecessarily.

AI cost and provider controls

  • Set a maximum spend and token budget per task and per account.
  • Route tasks to the smallest capable model; reserve stronger models for genuinely complex work.
  • Cache reusable extraction or research results where lawful and appropriate.
  • Do not call AI for repeated template assembly or standard interpretations.
  • Track cost per successful extraction, approved narrative block and report—not merely total tokens.
  • Provide user-visible indication when an optional AI task may incur cost or use an external provider.

13 · Final architecture acceptance checklist

What must be true before we call this architecture implemented.

  • □ Current repository and deployed architecture have been inspected and mapped.
  • □ Standard report and DPR are profiles over one canonical project model.
  • □ Financial and technical calculations are deterministic, versioned and independently tested.
  • □ Every important metric has a stable ID, formula ID, unit, period and lineage.
  • □ Every material claim is sourced, labelled as an assumption or shown as missing.
  • □ Report composition uses reusable content atoms and compatibility rules—not whole-document duplication.
  • □ HTML and PDF are rendered from the same semantic document tree.
  • □ A standard report can be generated with the AI provider disabled.
  • □ AI outputs are proposals, validated and confirmed before becoming project facts.
  • □ Paid report data is protected at the API boundary, not just hidden in the interface.
  • □ Golden project suite, regression tests, visual tests and tenant-isolation tests pass.
  • □ Engine, rules, content and renderer versions are captured in every report manifest.
Final recommendation: approve this architecture as the target direction. Do not begin by rewriting the existing FinSight codebase. Start with a repository audit, map what already works, identify duplicated or weak boundaries, and implement the canonical model and report compiler incrementally. The aim is to turn the existing product into a coherent report factory—not to discard working assets in pursuit of architectural purity.
