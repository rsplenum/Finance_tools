FinSight · Technical strategy and product architecture

Build the engine with AI. Run the business on deterministic code.

A detailed architecture for creating highly customised, lender-oriented project reports with minimal runtime AI, auditable calculations, reusable content components and combinatorial report assembly.

Recommendation

Yes — this is the right strategy, provided we engineer verification as seriously as generation.

Use AI agents aggressively during development to research, design, code, generate tests, challenge assumptions and improve the content library. 01 · Is the user’s thesis correct?

Correct in principle. Add one critical safeguard: independent verification.

Your core argument is sound. A report-generation business should not pay an LLM to re-derive financial logic, recompose standard schedules or rewrite the same predictable explanations for every customer. Those jobs are better handled by code that is deterministic, versioned and testable.

01

Lower marginal cost

Once code, rules and templates exist, another report mainly consumes compute, storage and rendering resources—not a fresh sequence of expensive model inferences.

02

Reproducibility

Same inputs, same engine version and same configuration should produce the same calculations and substantially the same document. Differences can be traced to changed inputs, rules, data or software versions.

03

Auditability

Every output can be traced to a formula, rule, content block, source record or renderer. A defect can be isolated, corrected and regression-tested.

The qualification: deterministic software is not synonymous with correct software. A hard-coded wrong tax treatment or a mistaken working-capital formula will be repeatably wrong. Correctness comes from specifications, independent review, test fixtures, reconciliations, version control and controlled releases.

02 · Know the boundary

What code can do exceptionally well — and what it cannot know.

Strong fit for code

Repeatable transformation

  • Calculate from defined inputs.
  • Apply explicit policy and accounting rules.
  • Generate schedules, tables and charts.
  • Check totals, ratios, units and cross-document consistency.
  • Select relevant sections based on project attributes.
  • Render the same content in HTML and PDF.
Requires evidence or judgement

World interpretation

  • Whether customers will actually buy.
  • Whether a promoter can execute the plan.
  • Whether a supplier quotation is commercially credible.
  • Whether a market claim is representative.
  • Whether a proposed technology is appropriate in a specific context.
  • Whether an unusual risk has been overlooked.

Code can calculate a reachable sales plan from customer count, conversion, order size and price assumptions. It cannot invent the customers. Code can estimate electricity consumption from machine load, operating hours and load factor. It cannot know the actual local supply reliability without evidence. Code can produce a risk register from known risk categories; it cannot guarantee that all project-specific risks have been discovered.

Design principle: when the system does not know, it must ask, disclose an assumption, flag a gap or offer optional AI-assisted research. It must never fill an evidence gap with confident-sounding prose.
03 · The millions-of-permutations question

Do not write millions of templates. Compose reports from reusable parts.

The mistaken assumption is that every different report needs its own complete template. It does not. A report is a composition of modules, content blocks, data, rules, evidence and presentation choices. A relatively small library can produce a very large number of valid combinations.

Analogy: a newspaper does not have a separately authored edition for every reader. It has reusable story units, sections, editorial rules, data and layouts. A content-management system assembles the edition. FinSight can assemble a project report in the same way—but with stricter financial and evidence controls.

04 · The proposed technical architecture

A report compiler with one canonical project model.

Every subsystem should read and write defined data contracts. Avoid independent modules copying values into their own stores. One canonical project model feeds calculations, narrative slots, tables, charts, checks and output documents.

Project modelFacts, inputs, evidence, assumptions
Domain enginesTechnical and financial calculations
Rule engineSections, validations, conditions
Content compilerNarratives, exhibits, schedules
RendererHTML, PDF, annexures

1. Canonical project schema

Typed, versioned entities for borrower, promoter, project, products, location, capacity, assets, costs, funding, operations, assumptions, evidence and financial periods. Every field has a definition, unit, validation rule and source status.

2. Domain calculation services

Separate pure functions for production capacity, input consumption, cost estimation, working capital, depreciation, taxation, P&L, balance sheet, cash flow, debt schedule, DSCR, break-even and scenarios.

3. Rules and orchestration

Determines which modules apply, what inputs are required, which conditions are satisfied, what exhibits are useful, what caveats are necessary and which sections should be omitted.

4. Content block library

Reusable paragraphs, tables, callouts, process diagrams, metric cards, risk rows, evidence notes and exhibit definitions. Each block declares required data and applicability conditions.

5. Narrative assembly

Combines authored templates, rule-driven sentence variants and approved metric references. It selects language based on actual results, project attributes and evidence status.

6. Document compiler

Orders blocks, applies layouts, page rules, headers, footers, page numbering, cross-references and annex bookmarks. The same source content feeds HTML and PDF.

05 · How the content library works

Think in content atoms, not whole-document templates.

A content atom is the smallest reusable unit that makes one useful contribution to the report. Atoms are composed into sections; sections into chapters; chapters into a report profile. Each atom has a contract.

Atom typeExampleContract
Fact blockPromoter and enterprise profileRequired fields, evidence labels, display rules.
Analytical blockCapacity utilisation analysisMetric inputs, formula IDs, interpretation conditions.
Table blockMachinery and equipment scheduleColumn schema, units, totals, source references.
Exhibit blockSales ramp-up chartDecision question, dataset, chart type, caption.
Narrative blockDebt servicing interpretationApproved metric tokens, conditional wording, caveats.
Evidence blockQuotation registerDocument ID, date, supplier, scope, exclusions.
Risk blockRaw material price riskTrigger, exposure, mitigation, owner, scenario link.

Example: one DSCR explanation, multiple valid outputs

The narrative is not generated from scratch. A tested rule selects a carefully written interpretation based on the metric, the period and the evidence.

Condition A

Coverage above the configured comfort threshold

“Projected cash accruals provide coverage of scheduled debt service throughout the forecast period. The lowest coverage occurs in {period}, at {minimum_dscr} times.”

Condition B

Coverage positive but tight

“Debt service remains covered in the base projection, although the margin is limited in {period}. The repayment profile is sensitive to {driver}.”

Condition C

Coverage below 1.0x

“The base projection indicates a debt-service shortfall in {period}. The funding and repayment structure requires revision before the forecast can support the proposed obligation.”

Thresholds must be configurable by product policy and context, not treated as universal lending standards. These are illustrative editorial patterns, not credit decisions.

06 · Make reports feel individual

Variation should come from facts, analysis, selection and editorial composition.

A deterministic report can still be highly individual. Personalisation does not require free-form prose on every page. It requires the system to select and compose the right content for this project's actual circumstances.

Data-driven variation

Different products, capacity, prices, locations, operating days, funding mix, costs, customers, suppliers and timelines produce different tables, calculations and conclusions.

Rule-driven variation

Expansion projects get existing-vs-proposed capacity. Seasonal businesses get seasonality analysis. High receivables get debtor-cycle analysis. Import-dependent projects get foreign-exchange and supply-chain risks where material.

Evidence-driven variation

Order-backed sales, quotations, promoter estimates and missing evidence receive different labels, explanations and annex references. The system never pretends they are equivalent.

Editorial variation

Alternative approved headings, sentence patterns, section openings, exhibit arrangements and levels of detail keep the output natural without randomising facts or changing meaning.

Example: expansion versus greenfield

Report elementGreenfield projectExpansion project
Business baselinePromoter experience and proposed business model.Existing operations, historical performance and current capacity.
Capacity analysisProposed installed and practical capacity.Existing capacity, utilisation, bottleneck and incremental capacity.
Market analysisInitial market entry and customer acquisition.Incremental demand, existing customers, new segments and cannibalisation.
Project costFull initial setup cost.Incremental investment, replacement and integration costs.
Financial modelStart-up ramp-up and stabilisation.Existing base plus incremental project economics.
Risk analysisExecution, commissioning and market-entry risk.Disruption to current operations, integration and demand risk.
Do not use random variation. Randomly changing adjectives, headings or chart styles can make reports look different while reducing coherence. Use controlled editorial variants selected by meaning, audience and report context. Every variant should preserve the same factual proposition.

How many templates do we actually need?

Think of a library of perhaps dozens of chapter layouts, hundreds of content atoms and a controlled set of narrative patterns—not hundreds of complete reports. The exact count should emerge from user testing and real project diversity. A good content atom should be reusable across many reports, but it should not be forced into contexts where it does not fit.

07 · Maximise AI during development; minimise it at runtime

Use AI as the engineering workforce, not as the production calculator.

AI agents can be used extensively to research domain methods, draft specifications, create code, generate test fixtures, review edge cases, write documentation, inspect code dependencies and improve the content library. But AI-generated code must pass independent verification before it is trusted.

Development-time AI: high

Where to use agents aggressively

  • Research accounting, banking, technical and industry methodologies.
  • Translate specifications into typed schemas and pure functions.
  • Generate implementation code and migration scripts.
  • Create unit, integration, property-based and regression tests.
  • Generate edge cases and adversarial examples.
  • Review code for defects, security, performance and maintainability.
  • Draft and challenge narrative libraries.
  • Build sample reports and compare them against reference outputs.
  • Document formulas, assumptions, data lineage and release notes.
Runtime AI: selective

Where to use models only when justified

  • Extract structured facts from uploaded quotations or documents.
  • Summarise a user-supplied market study.
  • Draft an unusual project-specific narrative from approved evidence.
  • Help the user describe their process or business in structured fields.
  • Conduct optional research with citations and explicit source dates.
  • Translate or simplify language for a selected audience.

AI development workflow

GenerateAI writes code and tests
ChallengeSeparate review and edge cases

Do not let the same agent be the sole author and judge. It may reproduce the same mistaken assumption in implementation and tests. Use independently specified reference cases, manually checked calculations, external standards where relevant and independent review. AI review is useful, but it is not an oracle.

08 · Auditability, verification and release discipline

Make every number and paragraph traceable.

A robust engine needs more than unit tests. It needs specifications, independent reference calculations, data lineage, version control, regression tests and report-level reconciliation.

Formula registry

Each formula has an ID, definition, units, inputs, outputs, applicable project types, rounding policy, source/methodology, owner and version.

Assumption registry

Each assumption stores value, unit, period, source, evidence class, date, confidence, user confirmation and dependent calculations.

Metric lineage

Each displayed metric points to the exact calculation output, formula version and upstream assumptions. Charts and narrative bind to the same metric ID.

Report build manifest

Each report records schema version, engine version, ruleset version, content-library version, renderer version, source snapshot and generation time.

Testing strategy

Test layerWhat it catchesExample
Unit testsIncorrect formula or boundary behaviour.Interest calculation, depreciation, DSCR numerator/denominator.
Property-based testsGeneral invariants across many generated inputs.Increasing debt service without changing cash flow must not improve DSCR.
Golden-master testsUnexpected output changes after code/content updates.Known project inputs must match approved reference schedules.
Integration testsBroken links between modules.Project cost reconciles with funding and opening balance sheet.
Cross-document testsDifferent values for the same metric.Executive summary DSCR equals annex DSCR.
Scenario testsIncorrect propagation of shocks.Higher raw-material cost flows through P&L, cash flow and DSCR.
Renderer testsClipping, broken pagination, unreadable charts.Long company name, wide table, 30-year projection, missing optional sections.
Security testsUnauthorised access to paid or sensitive data.Unpaid user cannot fetch full report JSON or paid PDF from an endpoint.

Financial integrity controls

  • Use decimal arithmetic and explicit rounding policies for money; avoid accidental binary floating-point drift in financial totals.
  • Store currency, scale (rupees/lakhs/crores), unit and financial period as explicit metadata.
  • Define sign conventions for income, expenses, assets, liabilities and cash flows.
  • Reconcile opening and closing balances, sources and uses, debt balances and cash movements.
  • Never silently substitute a default for missing critical data.
  • Distinguish zero, unknown, not applicable and not provided.
  • Recalculate all dependent outputs when an assumption changes.
  • Keep historical report versions immutable; issue a new version when assumptions or engine logic change.
Auditability is not just “we can read the code”. It means a reviewer can trace a reported figure from the printed page back through its metric ID, calculation, formula version, inputs and evidence. Build that lineage into the product from day one.
09 · Build sequence

Develop the engine in layers, not as one giant agent task.

The best way to use AI to its technical limit is to give it bounded, testable work packages with explicit contracts and independent acceptance criteria.

01

Domain specification

Foundation

Define project archetypes, report depths, data dictionary, financial periods, evidence classes, units, sign conventions and the boundaries of what FinSight claims to provide.

02

Canonical schema

Foundation

Build typed schemas, validation, stable IDs, source records, assumption records and versioned migrations. No report design yet.

03

Financial core

Critical path

Implement project cost, means of finance, depreciation, P&L, balance sheet, cash flow, working capital, debt schedule, DSCR and scenario propagation. Validate independently.

04

First industry module

Critical path

Start with manufacturing: capacity, process, equipment, inputs, yield, manpower, utilities and implementation. Validate with real project examples and technical references.

05

Content atoms and rules

Composition

Build section rules, narrative patterns, exhibit contracts, evidence labels, omission rules and project-specific chapter composition.

06

HTML/PDF compiler

Presentation

Build one shared semantic report tree, accessible HTML, A4 print styles, page breaks, repeat table headers, annex bookmarks and visual regression tests.

07

Real-project validation

Field test

Run diverse anonymised project cases through the system. Have an independent credit/finance reviewer and a technical reviewer assess completeness, evidence and usability.

08

Additional archetypes

Scale

Add trading, services, food processing, construction and hospitality by extending schemas and domain modules—not cloning the entire report generator.

09

Selective AI and commercial controls

Optimisation

Add optional document extraction, evidence-assisted drafting, research, entitlements, payments, retention controls and cost telemetry.

How to instruct the coding agents

Every task should include: business requirement, mathematical or domain specification, input/output schema, invariants, examples, edge cases, prohibited behaviour, test requirements and acceptance criteria. Ask agents to explain assumptions and produce tests before implementation. Require a separate review pass and execute the tests in CI. Do not accept “looks correct” as an acceptance result.

10 · Economics and operating model

Make AI cost optional, visible and attributable.

A deterministic-first architecture makes the cost of a normal report predictable. It does not make the service literally free: hosting, storage, rendering, payment processing, support, data acquisition and security still cost money.

Suggested commercial packaging

Core report

Deterministic calculations, standard content library, project-specific report composition and PDF/Excel export.

No runtime AI required.

Evidence assist

Optional document extraction, quotation parsing, evidence classification and guided narrative assistance.

AI usage metered or included with limits.

Research / expert tier

Fresh market research, specialist technical modules or professional review where a qualified expert is engaged.

Separate scope, price and disclaimers.

Cost principle: do not spend an LLM token to repeat a calculation, format a standard table, select an obvious chapter or rewrite a stable explanation. Spend AI only where it creates value that code and existing evidence cannot provide economically.

Final answer to the central question

Yes, it is possible to generate millions of distinct, project-specific report configurations from a finite software system. The challenge is not the number of combinations. It is designing the configuration rules so that each combination is valid, relevant, evidence-aware and coherent. Start with a small set of archetypes and content atoms, prove the architecture on real projects, then expand the library based on actual gaps—not imagined template counts.

11 · Research and reference base

Why the architecture is defensible

The following external research supports the design principles. The proposed FinSight architecture is an engineering recommendation, not a claim that any single source prescribes this exact system.

UNIDO — Manual for the Preparation of Industrial Feasibility Studies. The manual's feasibility-study contents include executive summary, project background, market analysis and marketing concept, raw materials and supplies, location/site/environment, engineering, organisation, human resources, implementation and financial analysis. It is a strong source for the substantive modules the report compiler must support.
Official manual

PROBE — Benchmarking code generation in large language models (2026). The study evaluates functional correctness, proximity to valid solutions and code quality, and reports that generated code can fail on basic errors and harder tasks. This supports using AI to accelerate development but not treating generated code as production-ready without verification.
Research paper

From Generation to Verification (2026). A reproducible study compares LLM-assisted workflows and finds that greater verification activity did not automatically produce statistically significant correctness gains in its tested setting; more intensive verification also incurred substantially higher token and latency costs. This is a useful warning against assuming that simply adding more AI review loops guarantees quality.
Research paper

Guidelines for empirical studies in software engineering involving LLMs (2026). Useful context for defining evaluation protocols, validity and measurement when testing AI-assisted engineering workflows.
Research paper

Code review caution (2026). Research reports that LLM reviewers can misclassify correct implementations as non-compliant and that plausible explanations are not a substitute for executed verification. This reinforces independent tests and human review for critical calculations.
