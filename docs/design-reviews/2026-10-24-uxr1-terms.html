A critical review of the four tools' interface and experience

What will be reviewed, through whose eyes, by what method, and how each finding is graded and evidenced. Written before the analysis begins, so the analysis cannot choose its own yardstick.

“It is so simple to be difficult, but so difficult to be simple.”

1. The core statement, and how it is used

Every feature, hint, warning, option and caveat on these pages was added for a good reason. Each one alone is easy to add: that is how a tool becomes difficult. Making a tool simple means the opposite labour: deciding what the user does not need to see, say or do, and finding one control that does the work of three. The statement is therefore the test every finding is put to:

  1. What did it cost to make this difficult? Usually nothing: a line of text, a second button, an extra field, a note “just in case”.
  2. What would it cost to make it simple? A cut, a merge, a reword, a reorder: thought rather than code.
  3. Who pays for the difficulty? The borrower on a phone pays in attention; the lender pays in doubt; the DSA pays in time per file.

A finding is ranked high when the difficulty is large and the simple fix is cheap.

What “simple” means for each tool

DSCR statement

A borrower answers who they are and seven figures, sees one number with a plain verdict, and, if short, one way to make it work. Simple is: the answer and its verdict in one glance, the statement for the lender in one tap, nothing to learn before the first figure.

CMA

An accountant's form of many heads and years. Simple cannot mean fewer facts; it means the order of a CA's own working paper, one place for each figure, totals that check themselves, and the ratios a lender reads, not a wall of rows on a phone.

Project report

A long document built from a short interview. Simple is: a few plain questions, every assumption shown and changeable, the AI draft clearly a draft, and a report that reads as a lender expects, without the borrower having to know what a lender expects.

Construction estimate

A house in a few answers (plot, floors, rooms, city). Simple is: a credible total and cost a sq ft at once, the architect's rules stated not hidden, and room-by-room depth only for those who tap for it.

2. Scope

In: the four tool pages (/dscr/, /cma/, /project-report/, /estimate/) and every component under site/src/dscr, cma, report, estimate, the shared parts (fields.tsx, AmountField.tsx, Board.tsx, ToolHead.astro, Base.astro, ThemeToggle.astro), the documents (site/src/doc/ and each tool's document.ts), and home only where its scenes introduce a tool. Across the tools: consistency, the shared parts, and the journey from home to a downloaded document.

Out: the policy pages, the 404 and the site map (except as dead ends in the journey); engine maths and data values (figures are checked only against the engine's own output, never recomputed here); the explainer videos themselves (findings that touch them are noted for VID2).

Every state and path, each where it applies:

  • First visit, empty: what is read before the first question, what the page asks first.
  • The default path: only the owner's listed inputs (D-UX-10, D-UX-12), partly filled, then filled.
  • “More options” and expert modes: opened, a value changed, closed again.
  • Errors: an impossible value, a blank required field, text in a number field, a value out of range.
  • Empty and provisional results: a fact missing, how the page says what is needed.
  • Results: the answer, its verdict, what limits it, the plan when short.
  • Downloads: PDF, Excel and Word, and the printout; what each says and whether it is fit to hand over.
  • Back, reload and reopen: whether answers survive, whether the page says so.

4. Method

  1. A local build only (npm run build, served by scripts/serve-dist.mjs); no live website. If a website is truly needed, npm run hosts first and blocked hosts skipped.
  2. The repo's own instruments first: npm run design-review -- <page> (every state at 360, light and dark, with measured defects), npm run load (the twelve load counts against the baseline), the site check's axe, field-count and F9 results.
  3. A Playwright walk of my own, one script printing text only: the first screen's words, the order of questions, the error messages, what the result says, what changes on reload, the tab order, transfer sizes, and the text of each downloaded file. Screenshots only where text cannot answer a layout question, read once.
  4. Reading the component only to find a cause, never to judge what the user sees.
  5. Agents where they help: the critic for an independent pass on pages; the writer on wording against the load counts. Their findings are verified before they enter the report.
  6. Yardsticks: Nielsen's ten heuristics; WCAG 2.2 AA; docs/DESIGN.md's twelve principles and FinSight's rules; the repo's own rules: the default-path field ceiling (D-UX-10, D-UX-12), plain words, no defaults beyond defaults.json and architect.json (D-UX-08, D-UX-18), numbers only from the engine, never a missing fact defaulted, AI only as a marked draft (D-UX-44), the word “architect” never used for the tool (D-UX-18).
  7. Figures on screen are compared only with the engine's own output for the same inputs, never computed here.

5. Severity, and the evidence each finding needs

GradeMeaningExamples
BlockerStops a user or misleads them: a WCAG A/AA failure, broken navigation, an unusable phone layout, an answer that is wrong, hidden or unclear in what it means, a document a lender would reject.A result with no verdict; a required field with no label; a figure differing from the engine's
SignificantSlows or confuses on the default path; breaks a repo rule or a DESIGN principle; costs trust.A question above the ceiling; jargon on the default path; two primary buttons
PolishConsistency and finish.Spacing, a label's case, an icon that says nothing

Each finding records: page; state; width (360, 1024 or 1280); theme; what the user meets, in their terms; the evidence (a measured line, a quoted text, a count); the rule broken (WCAG criterion, Nielsen heuristic, DESIGN principle, D-id); and the difficulty against fix score below. A finding without evidence is dropped.

The core statement as a score. Each finding gets Difficulty 1–3 (how much it makes the tool hard: 3 stops or misleads, 1 is a small drag) and Fix 1–3 (3 is a wording or one-line change, 1 a redesign). Within each grade, findings are ranked by Difficulty × Fix: the highest are difficult things cheap to make simple.
