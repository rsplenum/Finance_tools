1. Overall verdict

You have built something more ambitious than an ordinary financial-calculator website. The strongest opportunity is not necessarily to add more tools; it is to make the capabilities you already have easier to understand, trust, and use.

Strong foundation

Engineering architecture

For an MVP, the separation between calculation logic, interface, document exports, policy data and optional AI endpoints is strong. There is a real domain engine, explicit assumptions, independent checks and a substantial test suite.

Needs validation

Financial correctness

Some banking conventions, thresholds and source values are explicitly marked unverified. Calculations can be internally consistent while still applying a rule a particular lender does not use.

Highest visible leverage

User experience

The visual identity has personality, but the homepage repeats its message and makes visitors work too hard to decide where to start.

Release gate

Commercial readiness

The complete build and test suite were not run in this environment. Source verification, real-user testing and appropriate legal review remain important before a broad launch.

Central conclusion: the machinery that produces financial documents is substantially developed. The next stage is to make that machinery understandable, trustworthy and effortless for the person who needs the document.

2. What has actually been built

The website presents four tools: a DSCR statement, a construction estimate, a project report and CMA data. The underlying repository is considerably more sophisticated than four simple calculators: it includes financial calculation modules, document-generation code, construction-cost estimation, CMA data, tests, design research and Cloudflare deployment configuration.

How the optional AI features fit

CMA statement reading

PDF text is extracted in the browser; selected lines go to the Worker and Anthropic. AI proposes references to source locations, the browser checks/copies the figures, and the user confirms them.

Structured facts and notes go to the Worker; AI drafts narrative sections; the application filters unsupported claims and figures; the user reviews the wording.

Good architectural boundary: AI assists with finding source figures or drafting prose. Deterministic code remains responsible for the financial arithmetic.

3. Have you figured out the engineering?

You have figured out a lot of the architecture. You have not yet proved the entire production system. Three different kinds of maturity need to be distinguished.

Level 1 — Does the software structure make sense?

Yes, largely. Pure calculation modules are separated from the UI. Different modules have corresponding check functions. Financial data is kept in explicit configuration files rather than being scattered entirely through UI code.

The implementation has meaningful depth: CMA checks calculations across financial years and forms; the project-report engine tests whether the balance sheet balances; the DSCR engine independently recalculates important totals; and the construction system calculates quantities before applying rates.

Level 2 — Do the calculations agree with themselves?

The initial evidence is encouraging. The archive contains 34 test files covering DSCR, repayment schedules, project reports, CMA, tax, construction estimation, quotation checks, narrative validation and document output.

The standalone 28-module engine/ TypeScript layer compiled successfully. A representative DSCR case from the test suite returned the expected yearly ratios, average DSCR and weakest year.

Important limitation: the complete npm run verify pipeline could not be run. Dependencies were not fully installed, a package was missing from the offline cache, and network installation timed out. The full Astro build, Worker typecheck, Vitest suite and browser/accessibility checks remain unverified in this audit.

Level 3 — Are the numbers appropriate for real financial decisions?

Independent check functions can establish that two implementations produce the same answer. They cannot establish that the underlying banking convention, benchmark or source rate is correct.

Arithmetic verification

Do calculations agree, balance and obey expected mathematical relationships?

Method verification

Does the formula represent the correct accounting, tax, scheme or lender convention for this use case?

Real-world validation

Can a borrower or professional understand the assumptions and use the output appropriately?

The first area is substantially developed. The next milestone is to close gaps in the second and third.

4. Financial correctness and trust

Your source files explicitly record uncertainty in some areas. That is good engineering. The next step is ensuring the interface and downloadable documents respect it.

A. DSCR: avoid implying a loan-approval verdict

The live DSCR page offers illustrative targets of 1.50 average DSCR and 1.20 minimum-year DSCR. It describes these as examples, not binding rules, and says the method has not yet been checked against primary sources.

Change “Will the loan pass?” to “Does your repayment projection meet this target?” Separate the calculated result, comparison target and source status.

B. Ratio and working-capital benchmarks

The CMA configuration says turnover-method percentages were read through search-result summaries rather than verified against underlying bank-policy pages. Some ratio benchmarks, collateral assumptions and loan-tenure limits are also marked unverified.

Until verified, describe these as illustrative modelling assumptions—not official RBI compliance requirements or universal bank limits.

C. Tax data

The tax file distinguishes information checked against owner-supplied legislation from values still based on secondary sources. Tax uncertainty can flow into profit after tax, cash available for repayment and apparent project viability.

Before broad public release, have applicable 2026–27 rates checked against final primary legislation by a qualified professional. Preserve tax year, regime, borrower type and verification status in the output.

D. PMEGP status needs reconciliation

The repository's scheme material describes revised PMEGP guidelines for 2021–22 through 2025–26, while the official MyMSME application page displays PMEGP activity for 2026–27 and an application entry point. This does not establish all current eligibility conditions, but it means the status should be reconciled with current official guidance.

E. Construction estimates: precision is not accuracy

A result such as ₹12,47,185 can be arithmetically exact while the real-world cost remains uncertain. Construction costs depend on site conditions, scope, city, labour, specifications, taxes, inclusions and local quotations.

Make a planning range the primary answer, with a detailed calculated estimate beneath it. Show assumptions, source date and items requiring local quotations.

5. Why the homepage feels redundant

The homepage includes a hero, a “Three tools at work” section, a “Four tools” section, a persona section, a cloud of feature/output labels, a privacy/capability statement, separate borrower and CA/DSA promotions, and a closing section repeating the main actions.

This is more than a subjective impression: the live homepage contains those sections, and the implementation repeats tool explanations in multiple formats. The examples section covers three tools while the next section presents four, which makes the repetition feel accidental.

Is the visual style itself “AI slop”? Not necessarily. Custom drawn/animated elements, fonts, ledger-inspired motifs, colour tokens, focus states and reduced-motion handling give the site more personality than a generic calculator template. The issue is that the page has too many competing explanations of the same product.

The design is being asked to make redundant content interesting. No design system can fully solve that. Apply the principle that every element needs a job to the page's information architecture, not just to individual components.

Your project docs prioritise Indian MSME borrowers preparing lender-ready documents, with CAs and DSAs as a secondary audience. The homepage gives several audiences nearly equal billing. If business-loan preparation is the core, prioritise that journey and present the construction estimator as a related but distinct tool.

6. Proposed homepage redesign

Reduce the homepage to four meaningful sections. This is a content/layout proposal, not a screenshot or a tested final design.

Section 1 · Hero

Prepare the numbers behind your business loan.

See your repayment capacity, build a project report or prepare working-capital projections. Review the assumptions and export the working papers.

What are you preparing?

  • Check loan repayment — DSCR statement for a business term loan.
  • Prepare a project report — costs, finance, projected accounts and repayment capacity.
  • Prepare CMA data — working-capital assessment and five years of financial figures.
  • Estimate construction or renovation costs — planning estimate and itemised quantities before collecting quotations.
Section 2

One worked example

Show a fictional case with a few inputs, the calculated result, one changed scenario and a compact list of assumptions. Let visitors see what the product produces before committing to a long form.

Section 3

How it works

Enter your figures. Review the assumptions. Export the working papers. Explain locally calculated inputs, download contents and the limits of a modelled result.

Section 4

Know what is calculated—and what still needs checking.

Explain source dates, assumptions, privacy and limitations. Put detailed policy and technical explanations behind links rather than requiring every visitor to read them before choosing a tool.

What to remove or demote

  • Remove separate animated demonstrations if the task selector and worked example already explain the product—or keep just one.
  • Remove the duplicated tool section, feature-chip cloud and one repeated CTA section.
  • Move audience-specific guidance to a “Who it's for” page or into each relevant tool.
  • Keep the hand-drawn identity, but use it to explain one financial idea or highlight one result rather than decorating repetitive sections.

7. Reducing cognitive load inside the tools

A. Make the next action obvious

The DSCR page shows “Provisional: 5 still to answer”, lists missing fields and then has a separate assumptions section. The provisional count is repeated again near the download area.

Suggested message: “Your calculation is not ready yet. Enter profit, sales growth and the three loan details below to calculate your first result.” Offer one action: Go to the next missing answer.

B. Give users a useful result early

Let users complete a short initial path, then reveal advanced options such as moratorium, instalment frequency, existing loans, additional income and lender-specific targets when needed. Progressive disclosure should reduce the amount users must understand at once, not merely hide options.

C. Turn assumptions into a manageable ledger

Show the three or four assumptions that materially affect the current result. Put the rest under one expandable “Review all assumptions” section. Each assumption should say what value is used, why it is used, and how changing it affects the result. Keep the full list in the exported report.

E. CMA should have two interaction modes

Guided entry

One financial year at a time, with explanations and visible reconciliation checks. Let users copy a prior year, import figures, and review copied or assumed values.

Accountant mode

A full grid with efficient keyboard navigation, paste support, year-by-year columns, clear validation and reconciliation indicators.

Start by asking “How do you have your figures?” and route users to statement reading, spreadsheet entry or manual entry. Explain that AI proposes source locations, the program copies figures, and the user must confirm the mapping.

F. Construction estimation should start with intent

Separate Create a planning estimate from Check a contractor's quotation. The user can choose the right mental model before answering questions about city, area, quality and work type.

8. Make the tools faster and more reliable

Performance

Repository review notes identify the construction-estimate page as heavier than other tools, with an estimated payload around 705 KB compared with roughly 401–443 KB for other tools. These are notes in the repository, not measurements independently repeated in a live browser.

  • Load document-export libraries only when a user requests a download.
  • Keep optional quote-comparison and advanced-estimation code out of the initial path where practical.
  • Use route-specific chunks and lazy-load optional UI.
  • Measure transferred/compressed bytes, time to usable interaction and calculation latency on a mid-range mobile device.

Calculation accuracy

Create externally validated golden cases. For each major model, use at least one case checked independently by a relevant CA, lender professional, quantity surveyor or other subject-matter expert. Keep the input facts, formula, source, expected figures and rounding rules together.

  • A worked example checks a particular answer.
  • Randomised/invariant testing explores broad classes of inputs.
  • Independent formula checks detect disagreements between calculation paths.

All three are valuable, but none replaces the others.

Financial-data freshness

The versioned data files and review-date checks are a good foundation. The repository's review-date script reported 29 data files and no overdue review violations under its configured rules. Make confidence visible to users and preserve location, rate basis, inclusions, source and date for construction prices.

Document generation

The download is the product's main deliverable, not an afterthought. Every report should state input figures, important assumptions, formulas/method where relevant, source and review dates, and which items need professional confirmation. A reader should understand the result without opening the website.

9. Security and privacy

Several choices are sound: ordinary calculations run in the browser; AI is handled by a separate Worker; input validation and call caps exist; AI features are optional; API keys are intended to be deployment secrets; event payloads are validated; and the D1 database has a retention mechanism.

The privacy page distinguishes ordinary local calculations from optional AI features, including sending selected statement text or narrative notes to Anthropic.

Recommended hardening

  • Request-size enforcement: enforce a true body-size limit that works when Content-Length is absent or untrustworthy, in addition to field-level caps.
  • Runtime response validation: validate AI response structure after parsing on the server; do not rely solely on provider structured output and TypeScript casts.
  • Interaction endpoint abuse: Origin/CORS checks are useful, but not authentication for arbitrary HTTP clients. Add sensible abuse controls to protect event data and database writes.
  • IP-based caps: ensure temporary client-IP counters in Cloudflare KV match the privacy notice and deployment implementation.
  • Reproducible environment: .node-version specifies Node major version 22, while the lockfile includes undici@8.11.2 with a minimum of Node 22.19.0. Declare a compatible version consistently in developer setup and CI.

These are practical hardening steps, not evidence that the application is fundamentally insecure.

10. What to build on top of this

Priority 1

A guided loan-file workspace

Start with “What are you trying to finance?” Collect reusable business facts once—borrower type, project details, financial history, costs, loan terms and existing borrowing. Route users to relevant calculations and generate DSCR, project report and CMA where applicable from a consistent set of facts.

Priority 2

A viability review, not just a verdict

Turn sensitivity/lever logic into a signature experience: “Your current projection misses the selected target. Here are the changes that could improve it.” Show which change has the largest effect, how much it changes the result and the trade-offs. Treat alternatives as modelled scenarios, not guarantees of lender acceptance.

Priority 3

An evidence and readiness checker

Before final download, show required inputs completed, assumptions still in use, checks that pass/fail/cannot be assessed, sources needing confirmation and supporting documents to collect.

Priority 4

A dedicated CA/DSA workflow

After validating the borrower journey, consider reusable client profiles, scenario comparisons, review notes, versioned documents and a clear record of changes. Validate the workflow before building substantial account, payment or collaboration infrastructure.

Scope warning: the current product is built around Indian lending terminology, MSME schemes, Indian tax settings and India-focused construction prices. A global SaaS requires a jurisdiction layer for taxation, lending conventions, financial periods, terminology, document formats and source provenance—not merely a currency selector. Keep the engine modular, but validate the Indian workflow before broadening scope.

11. Recommended 30-day plan

  1. Simplify the homepageReduce the page to one promise, a task selector, one worked example, three workflow steps and a concise trust section. Keep the distinctive visual identity.
  2. Remove ambiguity from resultsReplace implied lending verdicts with explicit comparisons against selected targets. Consolidate provisional status and assumptions into one obvious next action.
  3. Validate financial rulesComplete primary-source checks for material unverified DSCR, tax, ratio and scheme settings. Reconcile PMEGP guidance with current official status. Obtain independent worked examples.
  4. Test with five real target usersUse the usability script already in the repository. Give participants realistic tasks without explaining where to click. Observe hesitation, misinterpretations, backtracking and whether they can explain their results.
  5. Establish a dependable release gateRun the complete test suite, typecheck, Astro build, Worker build, site checks and accessibility checks in a correctly installed Node environment. Resolve failures before moving beyond the preview.

The live site is marked as a development preview and the repository prevents indexing on the Pages.dev domain. That is sensible; launch readiness should be deliberate rather than inferred from a polished homepage.

12. Audit scope and limitations

The review extracted the ZIP and inspected repository structure, application code, configuration, data files, tests, relevant design/product documentation and text extracted from source PDFs in docs/inbox. It traced key relationships across the calculation engine, UI and Worker.

  • All 38 JSON files parsed successfully.
  • The Worker JSONC configuration was structurally valid.
  • All .mjs scripts passed Node syntax checks.
  • 509 relative import references were inspected; the apparent SVG exception uses Vite's intentional ?raw suffix.
  • The standalone engine compiled successfully.
  • Documentation size, review-date and portable-skill checks passed.

The full application build and automated browser/accessibility suite could not be completed because dependencies were missing and could not be downloaded in the environment. A real headless-browser visual review of every viewport was not completed. This report therefore does not claim that every interaction was tested end-to-end or every binary asset was manually interpreted line by line.

Final assessment

The foundation is promising. The most valuable thing you've done is separate financial logic from presentation and keep calculations explainable and testable. That gives you room to improve the product without throwing away the engineering.

The next leap will not come from adding ten more capabilities or making the homepage more elaborate. It will come from making one user's journey exceptionally clear: I know what I am trying to prepare; I understand what information is needed; I can see what the model calculated; I know which assumptions matter; and I can confidently take the resulting document to the next stage.

Recommendation: pause feature expansion, simplify the UX, and validate the numbers and workflow with real users. That is how you turn a technically ambitious collection of financial tools into a product people understand, trust and return to.
