1. Expert assessment and revised DSCR script

My expert assessment: the direction is right, but I would change the creative brief before implementation.

Having reviewed the attached Analyzing Motion Graphics PDF and the proposed DSCR animation script, my recommendation is to proceed with HOME1c—but treat it as a carefully designed motion narrative, not simply a more elaborate animation.

The animation should explain the computation, not decorate it.

The reference uses connecting paths, moving pulses, a scanning magnifier, targeting brackets, kinetic text and components that lift and snap into place. These SaaS explainer techniques make invisible software processes understandable. FinSight can show where a ratio came from, which year is weakest, what causes the shortfall and what changes when an assumption is modified.

1. Verdict on Claude's six decisions

Live animation from engine figures — Agree

Use the same validated calculation result as the actual tool. Never maintain separate hard-coded financial values that can drift out of sync.

Marigold for motion, red for failure — Strongly agree

Marigold indicates activity, analysis and attention; red indicates a genuine failed test or shortfall; green indicates a defined passing test.

Lightweight animation helper instead of GSAP — Agree, with a caveat

SVG and CSS can handle line drawing, pulses, brackets, scanning and transitions. A small timeline utility is reasonable if testable and maintainable. Measure bundle cost; don't build a framework merely to avoid a dependency.

Stack the visual flow on narrow phones — Strongly agree

Do not shrink a desktop diagram. Stack inputs, calculation engine, annual results and weakest-year analysis vertically, with connections redrawn for mobile.

Captions rather than voice — Agree

Captions synchronise with figures, work silently and avoid voice-generation/localisation complexity. Make the captions available as ordinary text too.

Ten seconds of automatic animation — Revise

Ten seconds is not inherently too long; automatically replaying a complex animation while people read is the risk. Start with a tightly choreographed sequence and test it.

Recommended duration and controls

Start with 7–9 seconds for the full DSCR story. Prefer deliberate playback; test viewport autoplay separately. Do not relax the five-second motion rule globally. Define a narrow educational-explainer exception if needed:

  • No perpetual looping or automatic restart on scroll-back.
  • Visible replay and pause controls.
  • Reduced-motion mode that presents the same final result without animation.

2. Script: strong structure, four issues to resolve

The core sequence is inputs → calculation → target → shortfall → weakest year → intervention → improved result.

  • Too much in one sentence: use five short beats answering what is analysed, how it works, where the problem is, what can change, and what happens next.
  • Don't imply a longer term always fixes everything: recalculate the schedule and every year's DSCR; show the actual outcome, even if some years still fail. The result determines the animation, not the other way around.
  • Explain the shortfall: show cash available for debt service against debt service due, not just red rows.
  • Avoid competing effects: a lens, pulses, brackets, scan lines and glowing cards should not all demand attention simultaneously.

3. Revised five-beat DSCR script

BEAT 1 · 0–1.2 SECONDS

The inputs

“Start with the business and its proposed loan.” Data cards enter; connector lines draw toward the engine; one marigold pulse travels the path.

Motion: trim-path drawing, staggered reveals, travelling pulse.

BEAT 2 · 1.2–2.6 SECONDS

The calculation

“Each year's cash flow is compared with its debt repayments.” Annual rows appear with cash-flow bars, debt-service markers and computed ratios.

Motion: sequential reveal, numerical count-up, focus transition.

BEAT 3 · 2.6–4.2 SECONDS

Find the weakest year

“One year is the constraint.” The scan stops on the actual weakest year; red brackets identify a shortfall only if the target is missed.

Motion: scan sweep, target brackets, controlled focus pull.

BEAT 4 · 4.2–5.8 SECONDS

Test a change

“Now test a longer repayment term.” The term value lifts and slots into place; the schedule recomputes and affected values update.

Motion: corner brackets, spring-loaded slot-in, linked-value transition.

BEAT 5 · 5.8–8 SECONDS

Show the outcome

“See whether the revised schedule meets the target.” Ratios settle; the weakest year is checked first; only calculated results determine final status.

Motion: spring settling, restrained result reveal, semantic status transition.

These are proposed timings, not verified model results. If the scenario doesn't pass, the ending must show what remains below target. Finish on a stable, readable state.

4. Reference techniques and visual examples

Use SVG Bezier paths, trim-path drawing, spring entrances, travelling pulses, scanning and slot-in transitions selectively.

These are visual references, not frames from the supplied video.

Premium motion comes from causality, continuity, timing, hierarchy and restraint—not glow or effect density.

5. Engineering requirements

Separate animation from the calculation engine

Pass a typed, immutable snapshot of actual results to the animation. Never calculate financial outcomes in the animation itself.

type DscrAnimationSnapshot = {
  annualResults: Array<{
    year: string;
    cashAvailable: number;
    debtService: number;
    dscr: number | null;
    meetsTarget: boolean | null;
  }>;
  targetDscr: number;
  weakestYear: string | null;
  proposedTermMonths: number;
  revisedAnnualResults: Array<{
    year: string;
    dscr: number | null;
    meetsTarget: boolean | null;
  }>;
};

This is illustrative, not a claim these exact fields exist in the repository. Adapt it to actual engine types. No duplicated constants, invented intermediate results, or success stamp without evidence.

Build reusable motion primitives

DrawnPath, FlowPulse, FocusBracket, ScanSweep, ValueTransition, SpringCard, NarrationCaption, and ResultReveal. Keep the visual language consistent across DSCR, CMA, project reports and construction estimation, while tailoring the explanation to each tool.

Make the animation testable

Use a deterministic finite state machine. Test completion, replay, changed inputs, reduced motion, keyboard navigation, 360px layout, invalid inputs and the absence of misleading success states. Measure bundle impact and frame performance.

6. Future interactive version

After the first release is polished, offer “Try a different repayment term.” Recalculate the real model and update the weakest year, ratios and target comparison. First establish a high-quality reference implementation, then generalise.

7. Brief for Claude

Objective: Build a technically accurate DSCR motion explainer inspired by the supplied video. Explain the calculation, reveal the weakest year, demonstrate a proposed change and communicate the recalculated result.

  • Use five beats: inputs → calculation → weakest year → proposed change → verified outcome.
  • Target 7–9 seconds; deliberate playback, pause and replay; no looping. Test viewport autoplay separately. Keep the global five-second rule except for a documented narrow educational-explainer exception.
  • Marigold for active paths, red for genuine shortfalls, green only for verified passes. Avoid constant motion, gratuitous glitch effects and excessive glow.
  • Read design rules, HANDOFF, motion reference and current implementation before editing.
  • Use real engine outputs and existing fixtures. Verify the 60-to-80-instalment scenario; change the story if the model disagrees.

Acceptance: causal motion, engine-accurate figures, correct weakest year, recalculated outcome, readable mobile composition, and sophistication through timing and precision.

Final recommendation

Approve the work only when it achieves cinematic quality, explanatory quality and financial integrity. The guiding principle is: make the invisible computation visible.

2. How to fix the live-inspection limitation

How to fix this

Stop treating the live Pages URL as the only way to inspect the animation. Create a repeatable workflow to inspect the rendered page, observe motion over time, and compare it with the intended design.

  1. Access: Can the inspection environment open the Cloudflare preview?
  2. Observation: Can it capture the animation at the right moments, rather than only a static page?
  3. Verification: Do the visuals match the DSCR calculations and work on mobile?

Recommended workflow

1. Browser-based inspection

Open the exact preview in a real browser, wait for the page to settle, capture desktop and mobile screenshots, and inspect console errors, failed requests and layout overflow.

2. Capture motion

Record the animation end-to-end or capture frames at fixed timestamps. A final screenshot cannot establish whether the path draws smoothly or the correct year is highlighted.

3. Verify code and calculations

Inspect the component, animation state machine and DSCR engine. Run the scenario and compare displayed values, weakest year and final status with calculation outputs.
